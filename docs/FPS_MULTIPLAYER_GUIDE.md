# FPS 멀티플레이 학습 정리 — Silent Chapel에서 《Man's War King's St.》로

이 문서는 개발 초보자를 위한 정리입니다. Silent Chapel에서 직접 만들어 본 기술이 무엇인지,
그리고 경쟁형 FPS를 만들 때 **무엇이 더 필요한지**를 구분해서 설명합니다.

> 여기 나오는 FPS 기능(서버 권위, 명중 판정, 체력, 지연 보상 등)은 **성당 MVP에 구현하지 않았습니다.**
> 성당은 경쟁 게임이 아니므로 필요 없고, 이 문서는 다음 단계 학습을 위한 설명입니다.

---

## 1. 한 장 요약

| | Silent Chapel (지금) | 경쟁형 FPS (앞으로) |
| --- | --- | --- |
| 누가 위치를 정하나 | **각자의 브라우저** (클라이언트 권위) | **서버** (서버 권위) |
| 서버 역할 | 메시지 중계만 (Supabase Realtime) | 게임 규칙 실행, 판정, 보정 |
| 부정행위 | 막을 필요가 거의 없음 (경쟁 없음) | 반드시 막아야 함 |
| 전송 빈도 | 1~10 Hz, 움직일 때만 | 20~128 Hz (틱레이트), 항상 |
| 지연 처리 | 보간(과거를 부드럽게 재생) | 보간 + 클라이언트 예측 + 서버 보정 + 지연 보상 |
| 서버 비용 | 무료 플랜 가능 | 전용 게임 서버 필요 (Node/Go/Rust, Colyseus, Nakama 등) |

## 2. 성당에서 만든 모듈 (재사용 가능)

모두 `src/lib/` 아래에 있고 React·Three.js에 의존하지 않아 다른 프로젝트로 옮기기 쉽습니다.

| 모듈 | 파일 | 하는 일 | FPS에서 |
| --- | --- | --- | --- |
| PlayerState | `game/PlayerState.ts` | 위치·방향·자세를 담는 데이터 형태 | 체력, 무기, 탄약 등을 추가 |
| PlayerController | `game/PlayerController.ts` | 입력 → 다음 위치, 충돌 처리 (순수 함수) | **같은 함수를 서버에서도 실행** (결정적 시뮬레이션) |
| InteractionSystem | `game/InteractionSystem.ts` | 가까운 물체 찾기 | 문 열기, 아이템 줍기 |
| NetworkManager | `net/NetworkManager.ts` | 인증→입장→구독→송수신 총괄 | 서버 연결 계층으로 교체 |
| RoomManager | `net/RoomManager.ts` | 방 id 규칙과 채널 이름 | 매치/로비 관리 |
| PresenceManager | `net/PresenceManager.ts` | 누가 방에 있는지, 갱신 빈도 제한 | 로비·파티 상태 |
| PositionInterpolation | `net/PositionInterpolation.ts` | 받은 위치를 부드럽게 재생 | **다른 플레이어** 표시에 그대로 사용 |
| ReconnectionHandler | `net/ReconnectionHandler.ts` | 끊기면 점점 간격을 늘려 재시도 | 동일 + 매치 복귀 |
| protocol | `net/protocol.ts` | 메시지 형식·검증·전송 주기 | 바이너리 직렬화로 발전 |

### 2-1. 핵심 개념: 클라이언트 권위

```
[내 브라우저]  W키 → stepPlayer() → 내 위치 결정 → 방송("나 여기 있어")
                                                       │
                                     Supabase Realtime (그대로 전달만)
                                                       ▼
[친구 브라우저]  받은 위치 검증 → 버퍼 저장 → 150ms 전 시점을 보간해서 그림
```

장점: 단순하고 서버가 필요 없음. 단점: **내가 "나 벽 너머에 있어"라고 거짓말해도 서버가 모름.**
그래서 성당에서는 괜찮지만 FPS에서는 안 됩니다.

### 2-2. 보간 (Interpolation)

네트워크 메시지는 띄엄띄엄(예: 0.1초마다) 도착합니다. 받은 즉시 그 위치로 옮기면 아바타가 뚝뚝 끊깁니다.
그래서 **일부러 조금 과거(예: 150ms 전)** 를 보여 주면서, 그 시점 앞뒤 두 스냅샷 사이를 비율로 섞습니다.

```
받은 위치:   A(0ms) ────────── B(100ms) ────────── C(200ms)
화면 시점:                ↑ 지금-150ms = 50ms → A와 B의 중간
```

- 전송 빈도가 낮을수록 지연을 크게 잡아야 합니다(`interpolationDelayMs`).
- 너무 멀리 순간이동한 경우(앉기 등)는 보간하지 않고 바로 옮깁니다.
- 각도는 짧은 쪽으로 돌립니다(179° → −179° 는 2° 회전).

### 2-3. 이번에 겪은 실제 문제: "입장 폭풍"

처음에는 새 사람이 들어오면 모두에게 "위치 알려 줘"를 방송하고, **모두가 다시 자기 위치를 방송**했습니다.
10명 시뮬레이션에서 초당 메시지가 292건(무료 한도 100건)까지 치솟았습니다.
원인: 방송은 **모든 사람에게** 가므로 입장 1번에 (n−1)²건.
해결: 마지막으로 멈춘 위치를 Presence에 넣어 두면, 서버가 **입장한 사람에게만** 현재 상태를 보내 줍니다 → 90건/초.
교훈: **"모두에게 보내기"는 사람 수의 제곱으로 비용이 커진다.** FPS에서도 관심 영역(AOI)으로 보낼 대상을 줄입니다.

## 3. FPS에 추가로 필요한 것 (성당에는 미구현)

### 3-1. 서버 권위 (Server Authority)
클라이언트는 **입력만** 보냅니다("W키 누름, 마우스 3도 회전, 사격 버튼"). 위치 계산은 서버가 하고 결과를 모두에게 보냅니다.
```
클라이언트 ──입력(틱 번호 포함)──▶ 서버: stepPlayer(입력) → 충돌 → 판정 → 상태 확정
클라이언트 ◀──확정된 상태 스냅샷── 서버 (초당 20~60번)
```
- `PlayerController.stepPlayer` 처럼 **같은 입력이면 같은 결과**(결정적)인 함수를 서버와 클라이언트가 공유하면 좋습니다.
- Supabase Realtime은 메시지를 중계만 하므로 이 역할을 할 수 없습니다 → 별도 게임 서버가 필요합니다.

### 3-2. 클라이언트 예측 (Client-side Prediction)
서버 응답을 기다리면(왕복 80ms) 내 캐릭터가 늦게 움직여 답답합니다.
그래서 **내 캐릭터는 입력 즉시 스스로 움직여 보고**, 보낸 입력을 번호와 함께 보관해 둡니다.

### 3-3. 서버 보정 (Reconciliation)
서버가 "입력 #105까지 처리한 네 위치는 (3.0, 7.2)"라고 알려 주면:
1. 내 위치를 서버 값으로 되돌리고
2. 아직 서버가 처리 안 한 입력(#106~#110)을 다시 적용합니다.
예측이 맞았다면 차이가 없고, 틀렸다면(벽에 막힘 등) 살짝 보정됩니다.

### 3-4. 지연 보상 (Lag Compensation)
내가 화면에서 적을 정확히 조준해 쐈어도, 그 화면은 **보간 때문에 과거**입니다.
서버는 최근 ~1초 동안 모든 플레이어 위치를 기록해 두고, "이 사람이 쏜 순간 그 사람 화면에서 적은 어디였나"로 **되감아서** 판정합니다.
(되감기 최대치를 제한해야 핑이 매우 높은 사람이 유리해지지 않습니다.)

### 3-5. 명중 판정 (Hit Detection)
- 히트스캔: 총구에서 광선(ray)을 쏴서 되감긴 히트박스(머리·몸통·다리)와 교차 검사
- 투사체: 서버가 탄환을 물리적으로 이동시키며 충돌 검사
- **판정은 반드시 서버에서.** 클라이언트의 "맞았어!"를 믿으면 안 됩니다.

### 3-6. 체력·피해 계산
- 서버만 체력 값을 바꿉니다. 클라이언트는 표시만.
- 부위별 배율, 거리 감쇠, 방어구 등은 서버 설정 데이터로 관리 → 밸런스 수정 시 클라이언트 업데이트 불필요.

### 3-7. 충돌 판정
- 성당은 2D 원-상자 충돌(`collide`)로 충분했지만 FPS는 3D(계단, 경사, 점프, 엄폐물) 필요
- 서버에서도 같은 맵 충돌 데이터를 써야 합니다(예: Rapier, cannon-es, 직접 만든 BVH).

### 3-8. 부정행위 방지
| 치트 | 대응 |
| --- | --- |
| 스피드핵·순간이동 | 서버가 위치 계산 (클라이언트 위치를 믿지 않음) |
| 에임봇 | 서버 판정 + 통계 이상 탐지 |
| 월핵(벽 너머 보기) | 보이지 않는 적의 위치는 아예 보내지 않기 (관심 영역/가시성 필터) |
| 패킷 위조·재전송 | 인증된 연결, 순번(시퀀스)·시간 검증 — `protocol.ts` 의 검증이 출발점 |
| 사칭 | 서버가 연결마다 신원을 붙임 (지금 Broadcast는 이게 안 됨 → SUPABASE_SETUP.md 한계 참고) |

## 4. 추천 학습 순서

1. 성당 코드에서 `PlayerController.stepPlayer` → `NetworkManager.updateLocal` → `RemoteAvatars` 흐름 따라가기
2. `tests/net-sim.test.ts` 의 가짜 서버를 읽고, 메시지가 어떻게 오가는지 콘솔로 찍어 보기
3. Node.js로 아주 작은 권위 서버 만들기 (WebSocket, 20Hz 틱, 입력만 받기)
4. 클라이언트 예측 + 서버 보정 붙이기 → 일부러 지연(200ms)을 넣고 차이 체감
5. 히트스캔 + 지연 보상
6. 기성 프레임워크 비교: Colyseus(Node), Nakama, Photon, Unity Netcode 등
