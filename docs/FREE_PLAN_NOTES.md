## 1. 한도 (Free)

| 항목 | 한도 |
| --- | --- |
| Realtime 동시 접속 | 200 |
| Realtime 메시지 | **초당 100건**, **월 200만 건** |
| Presence 메시지 | 초당 20건 |
| 채널 입장 | 초당 100회 |
| Broadcast 페이로드 | 256 KB |
| 월간 활성 사용자(MAU) | 50,000 (익명 사용자 포함) |
| DB 용량 | 500 MB |
| 활성 프로젝트 | 2개 |
| 비활성 일시정지 | 1주일 동안 활동이 없으면 프로젝트 일시정지 |

**메시지 세는 법:** 클라이언트가 **보내거나 받는** WebSocket 메시지가 각각 1건입니다.
한 명이 위치를 보내면 `보내기 1 + (같은 방 다른 사람 수)만큼 받기` 가 됩니다.

## 2. 이 앱의 계산식

n명이 각자 초당 h번 보내면 → 초당 약 `n × h(보내기) + n × (n−1) × h(받기) ≈ n² × h` 건.

그래서 `src/lib/net/protocol.ts` 의 `sendRateHz()` 가 `h = 예산 / n²` 으로 전송 주기를 자동으로 낮춥니다
(기본 예산 80건/초, 최대 10Hz, 최소 1Hz).

| 접속자 | 전송 주기 | 모두가 계속 걸을 때 (초당) | 비고 |
| --- | --- | --- | --- |
| 2명 | 10 Hz | 40 | |
| 3명 | 8.9 Hz | 80 | |
| 5명 | 3.2 Hz | 80 | 보간 지연 약 500ms |
| 10명 | 1 Hz (하한) | 100 | 한도에 근접. 시뮬레이션에서 수신 90건/초 측정 |

- **멈춰 있거나 앉아 있으면 위치를 보내지 않습니다.** 멈춘 순간 1번, 이후 20초마다 1번만 재전송합니다.
  성당에서는 대부분 앉아서 기도하므로 실제 사용량은 위 표보다 훨씬 적습니다.
- 새로 들어온 사람은 **Presence 초기 상태**(서버가 입장자에게만 보내 줌)에서 기존 방문자의 마지막 위치를 받습니다.
  예전 설계처럼 "입장할 때마다 전원이 위치를 다시 방송"하면 입장 1회에 (n−1)²건이 생겨,
  10명 시뮬레이션에서 초당 292건까지 치솟았습니다. 현재 설계에서는 90건/초입니다.
- Presence(초당 20건 제한)는 닉네임·앉기 상태·멈춘 위치만, 최소 2초 간격으로 갱신합니다.

## 3. 월 200만 건이면 얼마나 쓸 수 있나 (대략)

- 10명이 함께 있고 **30%의 시간 동안 움직인다**고 가정: 100건/초 × 0.3 = 30건/초 → **시간당 약 10.8만 건**
  → 월 200만 건 ≈ **약 18시간**(10명 동시 기준)
- 3명이 1시간 동안 30% 움직임: 80 × 0.3 × 3600 ≈ 8.6만 건 → 월 약 23시간
- 혼자 머무르면 받는 사람이 없으므로 보내는 메시지만 셉니다(움직일 때 10건/초).

### 방 10개(최대 100명)일 때

방이 나뉘면 메시지는 **방마다 따로** 계산되므로, 100명이 한 방에 있을 때(초당 약 1만 건)보다 훨씬 적습니다.
그래도 프로젝트 전체 한도(무료 초당 100건, 월 200만 건)는 모든 방이 함께 씁니다.

| 상황 | 대략의 초당 메시지 |
| --- | --- |
| 10개 방이 모두 꽉 차고, 30%의 시간 동안 움직임 | 약 300건 → **무료 초당 한도 초과** |
| 3개 방에 30명, 대부분 앉아서 기도 | 수십 건 → 한도 안 |

방이 많이 찰수록 위치가 늦게 보이거나 끊길 수 있습니다. 실제로 많은 방이 동시에 차면
Supabase 대시보드의 **Usage** 를 보고 예산(`NEXT_PUBLIC_REALTIME_MSG_BUDGET`) 조정이나 Pro 플랜(초당 500건)을 검토하세요.

공개 서비스로 운영하면 무료 한도를 금방 넘을 수 있습니다. 운영 전에
1) 예산(`NEXT_PUBLIC_REALTIME_MSG_BUDGET`)을 낮추거나, 2) 방 정원을 줄이거나, 3) 유료 플랜을 검토하세요.
**유료 전환은 프로젝트 소유자가 직접 결정**해야 합니다.

## 4. 사용량 확인 방법

- 앱: 설정 → **네트워크 정보 표시** → 초당 보낸/받은 메시지 수, 누적 개수, 바이트
- Supabase 대시보드: **Reports → Realtime** 또는 **Usage** 페이지

## 5. 하지 말 것

- 위치를 PostgreSQL에 매 프레임 저장하지 않기 (이 앱은 저장하지 않음)
- Presence를 매 프레임 갱신하지 않기 (이 앱은 최소 2초 간격)
- 운영 프로젝트에 부하 테스트 실행하지 않기
